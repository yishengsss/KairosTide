# Kairos AI 受限管理权限设计

日期：2026-09-26
状态：待用户审阅；未批准实施计划。
范围：MiMo 助手的受限事件/任务管理闭环，不包括让模型控制 Kairos 系统状态。

## 问题与目标

当前 MiMo 接入仅提供文本问答。Kairos 需要让助手在用户主动指令下管理少量、明确授权的业务内容，同时维持服务端业务事实与用户决定权。模型可以理解意图、调用受限工具并解释结果；它不能直接访问数据库、任意 HTTP、场景状态、时钟、提醒确认或冲突决策。

成功标准：明确的用户指令可经服务端确定性验证后管理被允许的数据；模糊或缺失信息会触发追问；模型不能绕过刚性事件确认；助手不能在未被询问时读取或推荐柔性任务；每次写入都可追溯到用户消息、校验结果和业务命令。

## 已确认的产品边界

- AI 可以协助管理有限的刚性事件与柔性任务。
- AI 不是系统控制者；FREE/场景、实际事件边界、提醒、请假和冲突选择由系统规则及用户决定。
- 柔性任务仅由用户主动添加，保存后隐藏；只有用户主动查询时才读取和展示。
- 刚性事件创建先形成草稿，信息完整且用户确认后才保存。
- 模型不能创建虚构任务或安排，不得以自由文本宣称已完成实际写入。

## 建议实施范围

采用受限工具调用（而非把权限写在 prompt 后接受模型文本）。模型只可返回以下工具之一，后端只实现窄命令：

| 操作 | 范围与触发 |
| --- | --- |
| 创建柔性任务 | 用户明确表达添加意图；标题必需，截止时间可选。后端校验并直接保存，除非模型字段缺失或解析不确定，此时先追问。 |
| 查询柔性任务 | 仅用户明确询问待办、未完成事项或临期任务时执行。读取范围由服务端固定；回答只依据返回的已保存任务。 |
| 修改/删除柔性任务 | 仅用户明确要求；必须唯一匹配任务并使用版本校验。工程建议：目标唯一且指令明确时执行；目标不唯一则先让用户选择。 |
| 查询刚性事件 | 用户明确询问后读取所请求的时间范围；不得将查询结果常驻显示在自然场景。 |
| 创建刚性事件 | 形成现有 DraftResponse 草稿；缺必填信息继续追问。只有明确的前端确认动作可调用 commit。模型的工具调用本身不构成确认。 |
| 修改/删除刚性事件 | 形成变更提案，必须确定目标与“本次/整个系列”范围；工程建议所有写操作由用户确认卡确认后执行。 |
| 本次请假/取消 | 作为实例级显式命令；必须精确定位单个 occurrence。不得推导系列变更或替用户做冲突选择。 |

当前实施不开放工具：自动安排自由时间、创建固定时段学习计划、选择冲突主事件/标记其他为 missed、改系统/场景时钟、改天气/位置设置、确认草稿、任意数据库或 HTTP 调用。

## 交互与执行流程

1. 前端向新 API 发送本轮文本、会话 ID、消息序号及客户端消息 ID；API 校验消息大小和会话版本。
2. API 将规范系统提示、允许的工具 schema 及必要上下文交给 MiMo。模型只提出 tool call；服务端校验工具名、参数、权限、目标身份及版本。
3. 纯查询工具由服务端执行，再将受限结果交给模型形成回答。柔性任务明确创建/变更可按上述确定规则写入；模型输出不得伪造工具结果。
4. 刚性事件草稿/变更提案与已保存事件分开持久化。前端展示结构化卡片；只有用户显式点击确认才调用正式提交命令。
5. 每个命令按幂等键防重，并在事务中做版本检查；失败保留用户原文、草稿和输入，不返回自然语言“已保存”。
6. 提供单独的受控错误响应；日志只记录操作类型、匿名实体 ID、版本、结果码和耗时，不记录 key、完整对话或精确地点。

## 架构边界

- `adapters/ai` 只负责 MiMo 协议与 JSON/tool-call 解码，不持有业务写权限。
- `application/assistant` 决定工具白名单、请求用户澄清、调用窄用例并格式化执行结果。
- `domain/tasks` 和事件领域验证有效状态；SQLite 仓库负责事务、owner 隔离、版本与幂等。
- API schema 是传输事实来源；变更后重生成 `contracts/openapi.json` 和 `contracts/backend-api.d.ts`。
- 前端将工具结果映射为回答、任务结果卡、刚性事件草稿/变更确认卡。任何未确认刚性提案不能显示为已保存事实。
- MiMo key 始终只在服务端进程环境中；不可发给前端、模型工具参数、日志或 repo。

## 安全及失败行为

- 工具白名单由应用代码维护，模型不能选择未注册工具、构造 SQL、任意 URL 或任意 endpoint。
- 模型返回无效 JSON、未知工具、伪造资源 ID、缺字段、过期版本或 owner 不匹配时，不产生业务写入，转为澄清或安全错误。
- 用户文本、事件标题和任务标题均为不可信数据，不可作为系统指令。
- 明确区分模型成功生成提案、应用通过验证、用户确认及事务提交四个结果；UI 仅按 API 结构化结果显示成功。
- API 超时/重试时以客户端消息 ID 与幂等记录避免重复创建；若结果未知则显示“结果未确认”，先查状态，不重复写入。

## 验收

- “周日前完成操作系统实验”按用户时区保存为柔性任务；“有哪些快截止”只读，不创建。
- 未询问时，页面启动、场景刷新、刚性事件到点均不访问柔性任务仓库。
- 缺截止日期或相对日期歧义时先追问，不编造日期；查询只引用服务端已有任务。
- 修改/删除在目标模糊时不写；重复任务 ID、过期版本、跨 owner ID 和模型伪造工具结果均拒绝。
- 刚性事件信息不完整时不创建正式事件；确认前数据库无事件/提醒；用户确认后恰好提交一次。
- 模型企图自动请假、冲突选择、固定安排自由时间或绕过确认时，服务端拒绝且无副作用。
- 到点时 AI 输入、草稿和焦点不丢；写入响应乱序不覆盖新状态。
- 覆盖离线单测、临时 SQLite 集成测试和真实浏览器 HTTP 旅程；外部 MiMo 在线评估与离线门禁分开记录。

## 分阶段落地建议

1. 将当前 `/assistant/chat` 升级为可版本化会话和结构化 tool-call 编排，但先只提供柔性任务新增、按需查询、明确目标修改/删除。
2. 建立刚性事件查询、Draft 草稿确认和实例级例外命令；补齐现有草稿/例外端点与前端卡片，保留“本次/系列”边界。
3. 独立完成冲突集合版本和用户选择命令；只有这一步完成后才向助手开放“冲突信息查询”，仍不开放助手替用户选择。
4. 完成真实浏览器和 MiMo 假模型越权评估；每阶段通过相应门禁后再开放下一批工具。

不得把“所有列出操作都完成”作为一次未经分解的实现承诺；分阶段实现，未接通能力由助手明确说明。

## 待用户裁定的实现提案

以下是减少误操作的工程建议，不是已确认产品决定：

1. 明确添加的柔性任务立即保存；明确且唯一目标的柔性任务修改/删除直接执行。模糊匹配时追问。
2. 刚性事件创建、修改和删除均先展示确认卡；实例请假/取消需要单独明确确认，始终只作用于精确定位的本次实例。
3. 重复系列管理在首轮仅支持查询与明确确认后的整系列操作；AI 永不自动改 series scope。
4. AI 回答当前使用单个用户会话；数据归属沿用现有单机 `owner_id=local` 工程基线，不在本次加入账户、多用户或跨设备同步。
