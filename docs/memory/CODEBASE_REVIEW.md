# Kairos 半成品研读记录

日期：2026-09-26。范围：现有 Vue 前端与 Python 后端的入口、核心领域、API 适配、草稿与状态链路、已有测试及历史架构文档。本轮没有修改功能代码，没有启动真实模型调用或写入用户数据库。构建产生了本地构建产物。

## 需求基准

以 `PRODUCT_MEMORY.md` 和用户最新说明为产品基准。两个子项目的第一版规划、旧执行计划及后端 AGENTS 中“不实现柔性任务”等内容与当前需求冲突，应视为旧阶段约束，不能覆盖用户当前要求。阅读历史计划不表示开始执行其中的任务或接受其中的产品假设。

现在已读取仓库中实际提供的第一版规划；此前产品记忆所说“未读取独立文档”描述的是建立记忆时的历史情况。旧文件包含与当前代码不一致的状态说明，应以代码与本轮实测分别判断实现及验证情况。

## 项目结构与可复用基础

- 前端：`XiAnHacker-view-v1`，Vue 3、TypeScript、Vite。`App.vue` 组合自然背景、当前事件和安排面板；`useSchedule.ts` 做状态同步、边界定时和离线缓存；`ScheduleApi` 下有 HTTP 与 localStorage Demo 两套实现，默认 Demo。
- 后端：`XiAnHacker-backend-v1/后端`，FastAPI、Pydantic、SQLite。domain 负责事件与实例展开，application 编排草稿和事件操作，adapters 对接数据库与模型，api 提供 HTTP。
- 后端已有草稿解析、澄清、编辑、确认、版本检查、幂等和事务基础。草稿固定初次解析时间，具有过期机制。
- 已有每天／每周重复、时区和 DST 处理、单实例请假／取消、系列更新／删除及 `[start_at, end_at)` 状态判断。
- 前端长按会重新读取 `new Date()`，已有约三秒隐藏、移动取消、键盘入口及减少动态效果支持。
- AI 面板到点不会被代码强制关闭，已有 active-banner 轻量提示；仍需验证和完善正式场景延迟呈现规则。
- 图片草稿是已有附加能力，但不应先于核心产品闭环投入；当前多候选 UI 存在风险，见下文。

## 与核心约束的偏差

| 方面 | 已读取的实际实现 | 与当前目标的差距 |
| --- | --- | --- |
| 主场景 | `App.vue` 常驻大标题、说明、安排 CTA 与多入口 | 自然环境尚未成为真正的默认主体 |
| 太阳与昼夜 | `NatureScene.vue` 太阳坐标固定，App 按 6 点／19 点生成 night 布尔值 | 缺少连续太阳轨迹、光照与色彩变化以及完整月亮星空表达 |
| 天气与季节 | 当前核心源码没有天气服务及季节驱动链路 | 真实天气、雨雪雾和季节环境需要实现 |
| 事件展示 | `ActiveEvent.vue` 显示起止时间、“正常参加”“这次请假” | 不符合隐藏数字时间及“知道了”“例外”的交互要求 |

| AI 管理 | `SchedulePanel.vue` 有问答／固定安排／已安排三个标签；助手后端只读 | 尚未实现以对话为主的修改、删除、请假与柔性事件操作 |
| 对话上下文 | UI 保存本次会话消息，但请求只有 question 与 timezone | 后端没有收到对话历史，澄清草稿之外的连续对话能力不足 |
| 状态协调 | 背景事件组件随 active 立即变化，dialog 留在前面 | 没有明确区分实际发生状态与对话结束后的展示状态 |

## 代码级风险与契约差异

以下来自静态数据流核对，尚未逐项新增回归复现，因此不等同于浏览器实测结果。

1. **例外状态丢失**：`src/services/api.ts` 的 `fromApiOccurrence` 丢弃后端 `status`，而后端 `/occurrences` 会返回标有 excused/cancelled 的实例。`useSchedule.ts` 离线回退仅按起止时间过滤缓存，因此这些实例有重新进入当前场景的风险；管理面板 `nextInstance` 也可能选到失效实例。
2. **多候选草稿可能被截断**：`SchedulePanel.vue` 的 `setDraft` 只把 `candidates[0]` 放入编辑器，`save` 将候选与单元素数组比较并 PATCH 为单元素。课表识别返回多个候选时，保存路径可能覆盖掉其余候选。
3. **HTTP 冲突确认未闭环**：适配器把所有草稿 `conflicts` 设为 `[]`，提交不传 UI 的 `allow_conflicts`；后端提交 schema 也没有该字段，提交路径没有接入冲突复检。Demo 的冲突提示不代表真实服务具有同等能力。
4. **文本重复创建受限**：后端 `DraftCommands.create` 调用 `_reject_text_recurrence`，文本模型提示词也排除不支持的重复规则；图片路径和手动候选路径的能力不同。不能依据数据库支持重复，就声称自然语言每周课程创建已打通。
5. **重复范围被前端补值**：`toApiCandidate` 对缺失的重复结束日期自动填入约 180 天后的日期。这是未获用户确认的安排范围推断，需消除或在草稿明确确认。
6. **生产 AI 请求仍被本地正则截流**：面板调用 `isFlexibleTask` 后直接返回本地建议，即使 HTTP 模式也不会保存柔性任务。`isFixedScheduleRequest` 同样在组件决定意图，容易与服务端理解不一致。
7. **接口文档落后于实际**：架构文档说 `/events` 返回系列，实际路由仍返回实例，前端使用 `/event-series`。API DTO 仍手写，没有历史计划提到的生成类型文件。README 对部分适配进度的描述也已滞后。
8. **Demo 与真实服务并非等价**：草稿过期、澄清参考时间、重复规则、冲突和实例状态处理有差异。既有 Demo 测试不能替代真实前后端联调。

## 后续开发顺序建议（未执行）

1. 先统一新需求与文档入口，定义提醒确认、事件实际状态、场景展示、冲突错过和 AI 草稿之间的边界；收敛前后端契约。
2. 补齐实例状态传递、多候选草稿和真实提交链路的关键问题，保留已有效的事务、重复与例外基础。
3. 建立符合约束的自然主场景和连续真实时间驱动，再接真实天气与季节表现。
4. 完成提前提醒、知道了关闭、未确认视觉增强、正式事件及对话不中断的联合状态流程。
5. 增加柔性事件的保存与查询，将事件管理收拢到 AI 对话，保留刚性事件确认边界。
6. 以真实 API 做端到端验收，覆盖长按真实时间、请假只影响单次、冲突用户决策、AI 到点不中断、跨午夜及后台恢复。

这不是已批准的详细实施计划；具体设计与开发应围绕用户当前目标继续细化，不能照搬旧收敛计划。
