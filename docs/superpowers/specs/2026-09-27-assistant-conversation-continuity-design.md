# Kairos 助手会话连续性设计

日期：2026-09-27  
状态：用户要求实施（2026-09-27）
范围：服务端会话存储、消息上下文构建与页面恢复

## 问题与目标

当前 `/api/v1/assistant/chat` 是无状态接口。浏览器每轮把内存中的完整文字记录发给服务端，而传输 schema 最多接受 24 条消息；正常每轮约新增两条消息，第 13 轮开始可能因请求超限失败。刷新页面会清空浏览器内存中的聊天记录和待确认草稿展示状态。已有 `/conversations`、消息写入与读取 DTO，但对应路由仍返回 501。

目标是让同一 Kairos 助手会话在多轮对话、页面刷新和请求重试后保持连续；已展示的待确认刚性事件草稿可恢复；长对话不会因 UI 不断累积消息而在传输校验处失败。刚性事件仍须用户确认后保存，持久化聊天不扩大 AI 的业务权限。

## 已确认约束

- 会话及记录必须按可信 `owner_id` 隔离，不能接受客户端指定所有者。
- 会话消息只存用户文字和助手文字，以及必要的结构化工具结果/草稿引用；不存 API 密钥、完整图片字节或图片 URL。
- 图片仅作为本轮临时请求输入。图片附件不进入持久化会话；页面刷新后不得伪装成图片仍可恢复。
- 草稿继续使用现有草稿仓储和确认摘要。会话记录只保存其 ID 引用；恢复时再从现有草稿接口读取当前版本和状态。
- 用户确认仍经现有草稿 commit 端点与幂等保护，不依赖模型重新解释“确认”。
- 会话历史恢复是只读操作；不得因读取历史自动查询柔性任务、天气或刚性事件。

## 设计

### 服务端会话为权威记录

实现已预留的会话接口：创建会话、按会话追加消息、分页读取消息。创建与读取均限制在可信用户所有权内。消息追加携带客户端消息 ID、期望序号及时区；重复 ID 且请求内容一致时返回原操作结果或继续同一待处理轮次，不重复完成业务写入；内容不同则返回冲突。序号不匹配时返回当前 revision/sequence，让客户端先恢复再重试。

追加消息由服务端读取会话历史，附加本轮用户文本后调用现有 AssistantService；客户端不再提交可任意改写的整段历史。模型调用前，仓储以短事务登记待处理用户轮次、规范化请求摘要和期望序号；同一会话此时不接受另一条新消息。模型调用不占用数据库事务。完成后以第二个短事务保存助手回复、可见工具结果、草稿引用并将该轮标记完成。刷新读取会显式标出待处理用户轮次，并返回该轮的 `client_message_id`；客户端用服务端原文与同一个 ID 重试，不自行生成新键；完成轮次的重试直接返回原响应。用户和助手消息保留稳定 ID、序号、角色及创建时间。服务异常不删除待处理轮次。

外部模型调用不能在 SQLite 写事务中执行。序号预留、请求幂等记录与响应完成由仓储事务保护；相同客户端消息 ID 和相同请求的重试复用已完成响应，或接续同一待处理轮次；不同内容冲突；其他新消息遇到待处理轮次时返回 409。AssistantService 已执行的业务写操作继续使用该客户端消息 ID 衍生的稳定动作 ID/幂等键，避免模型重试时重复创建任务或草稿。

### 上下文窗口

持久化记录保留完整文字会话并分页返回；每次模型调用最多使用最近 24 条完整 user/assistant 消息，且总文本不超过 32,000 个字符，按完整轮次从旧到新裁剪，不把半个回合留在窗口中。若最新输入无法放入窗口，返回可理解的校验错误，保留用户原文，不能静默丢弃。

短回答承接（如“持续20分钟”“确认”）继续依赖服务端当前会话记录与已有的上下文校验；不得依赖客户端伪造的旧 assistant 文本作为授权依据。有效的当前草稿经结构化引用恢复，不通过把旧确认消息塞进模型窗口重建。

本期不做模型自动摘要。摘要可能遗漏时间、否定词、单次/系列范围或用户拒绝等关键上下文；完整记录先持久化，近期窗口之外的信息不被伪装成模型已记住。若之后需要跨长时间跨度的语义检索或摘要，另行评估并用明确验收样本验证。

### 草稿恢复

消息响应包含其创建/更新的草稿 ID 引用。重载时先恢复最新消息页，再按引用调用现有 `GET /drafts/{draft_id}`。仅当服务端返回仍可编辑且未过期的草稿时恢复 DraftReview；已提交或过期草稿显示对应状态，不允许旧的 `ready` 缓存覆盖服务端状态。确认仍提交当前服务端返回的 revision、candidate IDs 和 confirmation digest。

用户在当前有效草稿后输入“确认”时，前端仍先直接调用既有草稿 commit 端点，不能让模型重新解释或执行保存。保存成功后，前端把确认这一轮提交到会话端点；若关联草稿已由同一 owner 确认提交，服务端追加一条固定确认回执，不调用模型或业务工具，仅用于维持 transcript 与 revision 连续。它不能提交或改变任何草稿。仅点击草稿按钮属于界面动作，不伪造用户聊天文本。

### 前端恢复与失败处理

浏览器持久化仅保存当前会话 ID，不保存聊天正文、图片字节或本地草稿快照。应用启动/首次打开助手时按 ID 从服务端加载会话；写入成功后才将服务端消息合并进 UI。请求超时保留输入与原 client message ID；先用会话读取接口核对该轮是否已经保存，不能盲目用新 ID 重放。

用户可从助手界面开启一个新会话；旧会话列表/搜索/删除不在本期范围。刷新恢复最近会话是本期行为。

## 传输与存储变更

- `conversations`：会话 ID、可信 owner、revision、创建/更新时间。
- `conversation_messages`：消息 ID、会话 ID、owner、序号、role、text content、时间戳、轮次状态、结构化 action result 与 draft refs；按会话和序号唯一。
- 会话级幂等记录：owner、conversation ID、client message ID、规范化请求摘要、请求文本及可重放的完成响应/待处理状态。
- 增加数据库迁移；不修改旧半成品目录。
- 延续已有的 `Conversation`、`MessageRequest`、`ConversationMessage`、`MessageResponse` 与 `MessagePage` DTO；若实现发现 DTO 无法表达幂等、当前 revision 或草稿状态，先更新 schema、OpenAPI 和生成类型再接入前端。

## 验收

1. 第 13 轮及更长对话不因 24 条请求数组上限失败；模型只收到完整轮次构成的受限窗口。
2. 创建用户 A 的会话后，用户 B 不能读取、追加或恢复 A 的会话/草稿引用。
3. 同一 client message ID 重试不产生重复消息、重复草稿、重复任务或第二条 assistant 回复；不同内容复用同一 ID 返回冲突。
4. 重启 API 后会话文本、序号、revision、待处理消息与未提交草稿引用可恢复；已提交/过期草稿不会显示为可确认。
5. 浏览器刷新后恢复最近会话及有效草稿，输入失败时保留原文并可安全核对重试。
6. 图片附件字节不写入 SQLite、会话消息、日志或错误响应；普通文本会话恢复不触发图片重放。
7. 读取会话不触发任何柔性任务/天气/日程查询工具。
8. 执行 API、Web、contracts 和迁移重启测试；浏览器真实旅程记录为独立验收，不以单元测试替代。

## 明确不做

- 不做用户登录、多设备账号同步、会话搜索、归档或删除 UI。
- 不把图片、图片 URL 或识别出的原图文件持久化。
- 不自动总结或压缩成未经验证的语义记忆。
- 不变更事件写入确认、冲突选择、AI 工具权限、天气问答或主场景状态规则。
- 不把对话持久化当作日程数据；正式事件仍只存在于事件/草稿仓储。

## 自审

- “完整历史持久化”和“受限模型上下文”分别定义，避免声称模型能永久记住所有旧轮次。
- 用户消息在模型调用前登记，超时重试沿用相同消息 ID；业务写入依靠现有操作幂等键保护。
- 模型调用置于数据库事务之外，并要求请求幂等以处理外部调用成功、响应落库失败的重试边界。
- 确认按钮继续读取服务端最新草稿，而非信任 localStorage 快照。
- 图片边界只约束二进制/URL持久化；本期不增加图片恢复假象。
- 现有会话端点是 501 骨架，实施涉及多层接口和迁移，需在用户审阅规格后形成执行计划。
