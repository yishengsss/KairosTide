# Kairos 验收与协作 Harness

日期：2026-09-26。状态：工程设计已部分落地；根检查器与T1 CI已实现，业务验收仍随各工作包补齐。

本文定义如何让新实现可读、可验证、可交接，不代表功能已完成。
适用新目录 `apps/web`、`services/api`；旧项目只作为只读参考。
本轮只编写文档；文中的目录、命令和证据路径除现有文档外均为目标接口。

## 1. 原则与事实来源

参考 [OpenAI Harness engineering](https://openai.com/index/harness-engineering/)：短入口、仓库内知识、机械边界和可观察反馈。
下述规则是针对 Kairos 的工程设计，不是对文章实验规模或自动合并方式的照搬。
不建立定时代理、自动通知或自动合并；技术反馈也不能变成产品里的任务催促。

事实按职责归属，避免同一规则出现多个可独立修改的副本：

| 内容 | 唯一维护位置 | 本文的职责 |
| --- | --- | --- |
| 已确认产品意图、最新澄清、待决定项 | [PRODUCT_MEMORY.md](../memory/PRODUCT_MEMORY.md) | 链接及映射验收，不升级猜测 |
| 旧实现与历史验证基线 | [CODEBASE_REVIEW.md](../memory/CODEBASE_REVIEW.md) | 仅引用，不借用通过状态 |
| 新架构、领域状态及 API 语义 | 新工程设计中各自指定的权威文档 | 检查引用与实现一致性 |
| 传输字段与错误模型 | `services/api` API schema 及其生成的 OpenAPI | 生成与兼容性检查 |
| 新实现是否可运行 | 当前代码及对应版本的实际验证证据 | 不以计划代替事实 |
| 验收方法、证据与协作规则 | 本文件 | 维护执行标准 |

`AGENTS.md` 保持简短，只给阅读顺序、事实来源、冻结边界和检查入口。
不要把整套状态机、测试表或旧计划拷进去；每个主题由链接进一步展开。
新用户澄清先进入产品记忆，再同步契约及受影响验收；变更记录标注来源和日期。
决策状态统一为“已确认产品规则 / 工程设计 / 暂定 / 待确认”。
文档检查只验证链接、归属、状态与映射完整性；语义是否符合意图仍需审查。

## 2. 新旧隔离与可执行依赖边界

以下是待实现的机械约束，不是当前已安装的 lint 规则。

| 区域 | 允许依赖 | 禁止依赖 |
| --- | --- | --- |
| `apps/web` 场景与交互 | 前端应用状态、领域视图、明确的端口 | 数据库、服务端内部、模型 SDK |
| 前端应用与领域状态 | 纯领域类型、时钟与 API 端口 | Vue 组件、DOM、真实网络及持久化实现 |
| 前端适配器 | 端口、生成的 API 类型、浏览器能力 | 通过界面正则绕过服务端持久化流程 |
| `services/api` 领域 | 纯类型、领域规则 | FastAPI、数据库、HTTP、模型或天气 SDK |
| 后端应用 | 领域与端口 | 具体数据库或外部服务实现 |
| 后端适配器与 API | 应用、领域、外部实现 | 越过应用用例直接修改业务状态 |
| 组合入口 | 选择并注入具体适配器 | 隐式全局时钟、运行期切换测试后门 |

冻结 `XiAnHacker-view-v1/**` 与 `XiAnHacker-backend-v1/**`：

- 新代码不得直接或间接 runtime import 旧目录，包括动态 import、路径别名、软链接和打包复制。
- 新安装清单不得把旧目录设为 workspace、editable dependency 或构建输入。
- 如需复用，显式移植最小模块到新目录，重审产品语义，并在新目录验证。
- 测试不能通过加载旧实现来让新验收通过；可将脱敏样本重新定义为独立 fixture。
- 历史文档可链接；历史源文件不得被新运行时读取执行。
- 未来 `python3 scripts/check.py architecture` 检查解析后的依赖图，而非仅 grep 字符串。
- 同一 architecture 检查比较任务开始时冻结目录的基线，报告任意内容变化；不自动回滚用户改动。

报错必须提供规则编号、违规边、来源文件和允许的修复方向。
不要以 blanket ignore、放宽全部依赖方向或排除整目录修复检查失败。
例外如确实必要，应有明确范围、负责人、理由和到期条件，并先进入架构决策。

## 3. OpenAPI 与前后端一致性

服务端 schema 是传输契约源；导出的 OpenAPI 和前端类型是可重复生成的产物。
目标导出位置为 `contracts/openapi.json`，生成类型唯一位置为 `contracts/backend-api.d.ts`，前端只导入这一产物。
生成产物禁止手改；OpenAPI 固定排序，锁定生成工具版本，消除无意义时间戳差异。
前端适配器负责传输类型到领域模型的映射，不能再维护第二套手写 API DTO。

每次契约变更必须完成以下闭环：

1. 同步语义文档、服务端 schema、示例和对应需求 ID。
2. 从新 API 导出 OpenAPI，再生成前端类型。
3. 在干净临时目录重新生成并比较，不允许检查过程静默修正工作树。
4. 检查真实 HTTP 的请求、响应、错误与 OpenAPI 一致。
5. 执行映射回归：状态、候选、重复规则、提醒确认、版本字段不可丢失或私自补值。

仅通过 TypeScript 编译不能证明运行期载荷正确；边界必须实际解析并拒绝无效数据。
演示适配器与真实 API 使用同一契约测试，不能用 Demo 通过替代真实 API 通过。
破坏性字段变更必须识别旧缓存和同步载荷的版本，不把解析失败悄悄当作空日程。

## 4. 可注入时钟与天气

三个时钟使用独立端口；生产中可共享真实来源，但消费者权限与测试实例分离。

| 端口 | 使用者 | 测试操控及不变量 |
| --- | --- | --- |
| `realClock` | 长按查时、实际时间读取 | 单独设为真实时间样本；不能引用其他两种时钟 |
| `sceneClock` | 太阳、月亮、光照与环境表现 | 可暂停/加速；不能改变真实查时或实例实际状态 |
| `scheduleClock` | 提醒窗口、事件边界、草稿时效 | 可推进至边界；不能改变长按显示或场景时间输入 |

浏览器纯渲染帧的计时不等于业务时钟；淡入淡出可用单调计时，不能驱动事件日期。
测试不通过全局替换 `Date` 同时冻结三种时钟；每个夹具列出三个端口的值与时区。
API 领域与应用禁止散落直接取系统当前时间；组合入口注入，必要的系统实现集中维护。
长按验收可将场景设为清晨、日程设为傍晚、真实时间设为 14:37，断言仅显示 14:37。
再仅推进其中一种时钟，检查其余消费者输入及输出不变，形成防串用测试。
刷新后的业务状态来自持久化和当前可信时间，不依赖某个浏览器定时器必须执行。

合成天气与固定时间是两个独立测试开关，不设置一个同时冻结全世界的“Demo 模式”。
天气 fixture 至少包括晴、多云、阴、雨、雾、雪及不可用/过期响应。
测试同一时间的天气变化和同一天气的时间变化，验证天气不会改变太阳时间位置。
季节、位置、时区的样本明确记录；服务来源及降级体验未确定时标为待确认。

测试入口只存在于开发/测试组合层，生产构建不导出控制路由、窗口全局变量或面板。
生产不得接受 URL、localStorage 或公开请求参数注入任意时间和合成天气。
未来生产隔离检查同时检查构建产物和启动后的行为，确认测试接口不可达。
本地假数据必须显式标识在开发工具中，不能在生产自然场景里常驻技术标签。

## 5. 需求 ID 与验收矩阵

本节是 K01–K17 的唯一索引定义处，其他设计文档引用这些 ID，不重复维护另一套编号。
各行写最低证据；尚未决定的细节只能验已确认不变量，不能用测试偷偷定产品行为。
U=纯领域/状态单元，I=真实 API 与临时存储集成，B=真实浏览器，V=视觉/可访问性审查。
所有行当前均为“未实施验收”；旧测试通过不迁移为这里的 PASS。

| ID | 行为与关键断言 | 最低证据 |
| --- | --- | --- |
| K01 | 旧目录冻结且不成为新系统的 runtime import、构建或安装依赖 | 静态：冻结基线差异、解析依赖图、生产产物检查 |
| K02 | 自然场景为默认主体；无常驻钟表、倒计时、进度、任务列表、下一事件或自由时间安排 | B+V：初始、FREE、事件结束截图与可访问性树 |
| K03 | 昼夜、太阳位置、光线、水面连续变化，sceneClock 与其他时钟互不污染 | U+B+V：边界采样、独立时钟与连续录屏 |
| K04 | 真实天气与季节作为独立环境输入，天气不改太阳时间位置；服务失败/过期不能伪装实时数据 | I+B+V：天气 fixture、独立真实服务测试；来源/降级体验待定 |
| K05 | 长按空白区域只临时显示真实时间，约三秒消失；模拟场景/日程不污染查时，不改变业务状态 | U+B：三时钟分离、取消手势与键盘等价入口 |
| K06 | 提前提醒显示事件信息；点击立即关闭，本地pending与服务端ack可跨刷新恢复；未确认可视觉增强而无数字倒计时 | U+I+B+V：网络延迟下即时关闭、失败不重弹、ack落库与安排版本校验、刷新、边界；提前量/重提醒策略待定 |
| K07 | 到点正常进入与结束退出不依赖 ack；按 `[start,end)` 求实际事件；无数字时间/倒计时或额外“开始”门槛 | U+I+B：开始前/开始/结束；正式 ack 收起范围待定 |
| K08 | 重复事件单次请假仅影响实例，后续系列不变；离线缓存不能把请假实例复活 | U+I+B：例外持久化、下一次展开、刷新/恢复 |
| K09 | 同时发生明确展示冲突，未选不默认选；用户选择主要事件后其余记录 missed，不删除实例或系列 | U+I+B：选择原子性、幂等、刷新；部分重叠/中途切换待定 |
| K10 | 柔性事件由用户主动添加并持久保存，不转换成固定日程；只可按用户确认的低频场景激励出现 | I+B：对话添加→刷新→主动查询/已授权的只读激励读取；无本地正则假成功 |
| K11 | 用户主动询问时可读取柔性事件；另可在 FREE 按每45–90分钟随机、每小时最多一次呈现已保存任务；助手打开、刚性事件活动或冲突未解决时暂停，不创建/安排/修改任务 | U+I+B：读失败不冒充空列表；无已存任务不生成提示；限定频率与FREE门槛；假模型不造任务/自动安排；真实语义另测 |
| K12 | 刚性事件解析→草稿→补齐→用户确认→保存；模糊时间/缺失地点不编造；未确认不参与提醒 | U+I+B：确认前零正式写入，重复确认幂等；管理对象/范围歧义先澄清 |
| K13 | AI 对话中到点只轻量提示，不关闭对话或丢输入/草稿；结束操作后按当时状态呈现 | U+I+B：实际状态与呈现状态分开；跨开始/结束并保留未发送输入 |
| K14 | 午夜无重置/总结；离线、休眠、重连和乱序响应不复活例外、不覆盖新 ack/选择、不重复写入或展示过期事件 | U+I+B+V：23:59→00:01、断网队列、恢复快照、逆序响应、版本竞争 |
| K15 | OpenAPI 生成与运行期契约一致；多个候选完整保留、展示、编辑、确认，不能只留首项；任一写入失败全部回滚 | 静态+U+I+B：生成零差异、至少三候选、第二项失败、重试及版本冲突 |
| K16 | 可访问、动效可中断且尊重减少动态效果；自然场景长时间运行稳定，技术 trace 不进入生产界面 | B+V：键盘/触屏/焦点、动效反转与退出、连续运行性能trace；测量方案见第6节 |
| K17 | 助手对话由服务端持久保存并按可信 owner 隔离；同一待处理轮次重试不重复执行；模型上下文限于最近完整轮次且保留最新用户输入；草稿恢复以服务端当前状态为准；图片载荷只在本轮请求中使用、不进入持久化字段 | I+U：重启后顺序读取多轮/待处理轮次/草稿引用，幂等重试及上下文边界（`test_conversation_api.py`、`test_conversation_recovery.py`）；全表检查图片字节与 data URL；Web session fake 验证过期草稿不能确认（`session-stale-draft.test.mjs`）。浏览器旅程及真实 MiMo 语义仍须单独验证 |

K06 的跨刷新只证明同一次 ack 保存与恢复；未来是否允许再次提醒需要单独决策。
K09 的 missed 语义按用户选择记录，不由客户端随意把所有重叠事件批量取消。
K11 的低频激励读取必须来自用户自己的持久化柔性任务；用真实 API/持久层与浏览器状态共同证明触发门槛和上限，不能仅用看不到提示的截图代替。
K13 若关闭 AI 时事件已经结束，不补演已经过时的正式场景；具体补充提示仍待确认。
K14 定义数据一致性不变量；离线可写范围、跨设备冲突策略须由契约决定后补充验收。
K16 的性能证据须注明设备、视口、场景和运行时长；不以高端设备的单张截图证明流畅。
K17 的图片隐私检查必须枚举 SQLite 用户表的全部已存字段；Web fake/API 测试不是浏览器或真实模型证据。模型上下文边界不能通过省略最新用户输入来满足。

## 6. 分层验证与真实体验证据

| 层级 | 环境与内容 | 不能据此声称 |
| --- | --- | --- |
| 文档/静态 | 文档链接、需求覆盖、类型、格式、导入图、冻结目录、秘密扫描 | 产品体验已经正确 |
| U | 无网络，独立时钟、确定种子；边界、例外、冲突、草稿状态、同步合并 | 数据持久化与 HTTP 已通过 |
| I | 新 API、临时数据库、真实事务；契约、候选原子提交、重试/竞争/版本 | 浏览器行为或真实 AI 能力已通过 |
| B | 新前端连接新 API；受控外部适配器、真实浏览器、实际输入操作 | 真实外部服务可用或视觉质量合格 |
| V | 场景截图/录屏、键盘/触屏、可访问性树、减少动态效果、视口 | 单一截图证明时间连续性或数据一致性 |
| 在线评估 | 单独连接真实 AI/天气，记录服务与模型版本、日期、预算、结果 | 离线门禁或未覆盖模型泛化能力 |

浏览器用例必须操作可见界面并核对 API/持久层关键结果，不能全靠注入状态跳过流程。
视觉证据标注需求、代码版本、浏览器版本、视口、像素比、时区、天气和三种时钟。
时间连续变化保存短录屏或固定间隔帧；视觉基线需审查批准，不能自动接受全部差异。
主场景检查亮暗天气下文字可读性、焦点可见性、遮挡、溢出与窄屏布局。
可访问性检查语义名称、焦点返回、键盘等价交互、触屏长按与滚动取消。
对话不会因事件到点失去焦点；视觉增强与减少动态效果需要共同验收。
不把隐藏时钟通过无条件 live region 播报；真实时间仅由用户主动交互触发。
高频场景帧不得反复向辅助技术播报事件或天气；自动扫描之外保留人工体验证据。

AI 假模型夹具覆盖：有效结构、模糊时间、缺字段、多候选、拒答、超时、无效 JSON、越权写入意图。
加入将“忽略确认”“泄漏秘密”“创建虚构任务”夹在用户材料中的不可信输入。
假模型只能测试应用护栏；真实语义理解必须用独立、版本化评估集验证。
无模型密钥也能完成所有离线检查；在线未运行必须明确记为 NOT_RUN。
天气真实调用与固定天气视觉验收分开记录，缓存及过期策略不能伪装成实时数据。

性能预算为待实测校正的工程目标：桌面60Hz下可见交互段帧时p95不超过20ms，雨雪可降粒子采样和分辨率；低端设备目标先维持30fps（p95不超过34ms）并保持输入响应。记录设备和浏览器，不把目标写成已通过数据。
运行30分钟连续场景，比较第5至10分钟和第25至30分钟的稳定内存样本；新增存活对象或监听器不能随面板开闭次数持续线性增长。后台5分钟应暂停装饰requestAnimationFrame，恢复后不补播历史帧。
主场景输入响应p95目标100ms以内，不把真实AI网络耗时归为按钮反馈。自动trace与人工慢放并行使用；硬件条件不同需记录偏差和降级结果，不能无限放宽阈值。

## 7. 观测、脱敏与排错

开发者 trace 连接 intent→draft→confirm→occurrence→ack/choice→presentation。
推荐结构字段：随机 trace ID、操作类型、实体匿名 ID、版本、结果码、耗时、重试次数。
记录实际事件状态与场景呈现状态分别变化的原因，便于定位 AI 延后展示和恢复问题。
不得记录密钥、授权头、完整对话、草稿自由文本、精确地点、原图或用户日程内容。
测试日志使用合成样本；故障证据导出前再次脱敏，并限制保留周期和访问范围。
生产错误给用户可理解的动作与恢复反馈；堆栈、版本竞争细节及 trace 面板只给开发者。
关联 ID 可以服务排查，但不为可观测性常驻显示技术徽标或污染自然场景。

## 8. 当前检查命令与覆盖范围

从根目录运行 `python3 scripts/check.py <docs|architecture|contracts|api|web|e2e|all>`。
当前 `scripts/check.py` 的 `docs`、`architecture`、`contracts`、`api` 与 `web` 已可执行；`e2e` 会以非零退出和 `NOT_RUN` 明确标记尚无浏览器旅程。每个需求仍需后续任务补充对应的业务测试与用户旅程证据，脚本通过仅证明其实际覆盖范围。

| 目标命令参数 | 约定责任 |
| --- | --- |
| `docs` | 链接存在、权威来源明确、K01–K17映射无悬空、文档状态齐全 |
| `architecture` | 新架构依赖方向、冻结目录无改动、旧目录 runtime 隔离、测试入口不进生产 |
| `contracts` | 临时目录重新导出 OpenAPI/生成类型，零差异、运行期契约与映射检查 |
| `api` | 后端格式/lint/类型、纯领域测试、临时数据库、新 API、事务/并发/同步与假模型测试 |
| `web` | 前端格式/lint/类型、状态/时钟隔离测试、生产构建及测试入口不可达检查 |
| `e2e` | 新前后端的真实浏览器流程、视觉/可访问性与性能证据，产出需求索引 |
| `all` | 汇总全部离线门禁；任何缺失或失败明确非零退出，不访问真实模型或天气服务 |

生成产物更新属于独立的显式操作；`contracts` 检查不静默改写工作树。
真实 AI/天气评估使用另行设计的显式入口，记录服务、模型、预算和日期，不隐含在 `all`。
秘密扫描纳入相关静态检查；生产隔离同时验证构建产物和启动后的实例行为。

统一返回约定：0=检查通过，非0=失败或无法完成；报告区分 FAIL、BLOCKED、NOT_RUN。
不得把缺少依赖、缺密钥、未实现命令或无匹配测试转成静默成功。
重复失败先保存最小复现，再判断是产品、契约、环境还是 Harness 本身缺陷。
修复反馈路径与对应回归；不能通过删断言、扩大容差或全部重录截图来掩盖问题。

## 10. 协调方式与依赖 DAG

推荐一名主协调代理加最多三名并行子代理；本文件不启动任何代理或执行开发计划。
主协调负责需求解释、契约冻结、任务划分、共享文件和整体验收，避免四方各定语义。
先冻结最低契约：实体 ID、实例状态、ack、missed、候选数组、版本/幂等、错误及三时钟端口。
冻结表示同一工作批次的共享接口固定；新需求仍可变更，但要先通知所有消费者。

依赖 DAG：需求与待定项 → 领域/契约冻结 → 三条实现分支 → 集成验收 → 独立审查。
三条分支可分别为后端领域/API、前端状态/交互、场景视觉/验收夹具。
只有无共享写入且依赖已满足的任务并行；业务状态未定时不把 UI 和 API 各自“先猜着写”。
审查代理应使用释放后的并发槽，不使同时活跃的子代理超过三名。

- 派工明确需求 ID、输入、输出、允许编辑文件、禁止范围、依赖版本与最低验证证据。
- 每个文件只有一个写入负责人；共享契约、生成产物、锁文件和根配置由主协调或指定人串行维护。
- 前端状态与视觉共享组件先拆清所有权；必要时只返回建议，由组件负责人整合。
- 子代理不得覆盖其他人的未提交改动，不以顺手重构扩大范围，发现冲突先上报。
- 契约变更后暂停受影响整合，更新文档、生成物与消费者，再恢复并行。
- 独立审查人读取真实 diff 和证据，重点审边界、产品负面约束与遗漏，不仅复述作者总结。
- 审查发现交给文件负责人修复，再针对受影响层级复验；最后由主协调核对跨端行为。
- 无独立审查槽时顺序安排审查，不把作者自评标为独立审查通过。
